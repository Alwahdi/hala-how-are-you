# حدود بيانات متابعة صاحب الشبكة

**الملخص:** تحقق مكتبي من وثائق مايكروتيك لتجنب تحويل الاحتياجات إلى وعود غير مختبرة.
الحقائق [confirmed] من المصادر، والاستنتاجات [assumption] تحتاج اختباراً على شبكات المؤسس.
لا يعتمد هذا الملف حلاً أو بنية للمنتج.

## الحقائق الموثقة
- مدير المستخدمين خادم RADIUS بحزمة منفصلة؛ الهوتسبوت وPPPoE يمكنهما استخدام حسابات محلية أو RADIUS. [confirmed] ([User Manager](https://help.mikrotik.com/docs/spaces/ROS/pages/2555940/User+Manager)، [PPP AAA](https://help.mikrotik.com/docs/spaces/ROS/pages/132350049/PPP+AAA))
- حفظ جلسات مدير المستخدمين يتطلب تفعيل محاسبة الجلسات على الراوتر؛ المصادقة وحدها لا تكفي. [confirmed] ([User Manager](https://help.mikrotik.com/docs/spaces/ROS/pages/2555940/User+Manager))
- RADIUS يسجل معرف المستخدم والجلسة وMAC العميل وعدادات الاستخدام ومدة الجلسة؛ اسم خادم الهوتسبوت ليس معرف نقطة البث المنزلية بالضرورة. [confirmed] ([RADIUS](https://help.mikrotik.com/docs/spaces/ROS/pages/328097/RADIUS))
- مدة الجلسة ليست مدة تشغيل نقطة البث؛ قائمة أجهزة Wi-Fi المتصلة تكون في بيانات نقطة البث نفسها. [confirmed] ([RADIUS](https://help.mikrotik.com/docs/spaces/ROS/pages/328097/RADIUS)، [WiFi](https://help.mikrotik.com/docs/spaces/ROS/pages/224559120/WiFi))
- مدير المستخدمين يدعم بدء الباقة عند إسنادها أو أول مصادقة، وتوثق مايكروتيك ترحيل قاعدة المدير القديم إلى الصيغة الجديدة. [confirmed] ([User Manager](https://help.mikrotik.com/docs/spaces/ROS/pages/2555940/User+Manager))

## استنتاجات تحتاج تحققاً على الشبكات [assumption]
- تفعيل الكرت لا يثبت بيعه أو تحصيل ثمنه؛ نحتاج سجلاً مستقلاً للبيع والتحصيل.
- MAC أو اسم المستخدم ليس هوية مؤكدة لشخص؛ ربط مشتريات متعددة بزبون يتطلب آلية هوية واضحة.
- في نقطة بث تعمل كجسر شفاف قد يرى الراوتر MAC أجهزة الزبائن، لكن نسبة كل جهاز لنقطة بث محددة تحتاج تمييزاً في الربط أو بيانات إضافية. ([Bridging and Switching](https://help.mikrotik.com/docs/spaces/ROS/pages/328068/Bridging+and+Switching))
- إذا كان مودم البيت ينهي جلسة PPPoE ويستخدم NAT، فبيانات الجلسة تمثل اتصال البيت ولا تكشف تلقائياً كل جهاز داخله.
- إجمالي الاستهلاك لا يعيد بناء تاريخ السرعة؛ عينات عدادات مؤرخة تسمح بحساب متوسط النقل بين العينات، لا سرعة الخط المتاحة.
- التوافق يحتاج فحص الإصدار والحزمة والجهاز والإعدادات؛ لا يكفي وصف «يدعم v6 وv7».
- RADIUS ليس بديلاً لنفق الوصول الإداري عبر CGNAT؛ حماية نقله لا تجعل واجهة إدارة الراوتر متاحة تلقائياً.

## تحقق إعدادات الباقة في User Manager v7
- هذا القسم يشرح معاني الإعدادات، ولا يكرر قيم مثال المؤسس؛ المثال محفوظ في [مصدر الاحتياجات](network-owner-workflows.md#الباقات-والنقاط-confirmed-المؤسس). [confirmed]
- `starts-when=first-auth` يبدأ تفعيل الباقة عند أول طلب مصادقة من المستخدم، بينما `assigned` يبدأ عند إسنادها. القيمة الافتراضية الموثقة `assigned`، لذلك يلزم اختيار البداية المطلوبة صراحة. [confirmed] ([User Manager — Profiles](https://help.mikrotik.com/docs/spaces/ROS/pages/2555940/User+Manager))
- `validity` يحدد مدة صلاحية الباقة؛ تفسيرها كنافذة زمنية من التفعيل، لا مجموع وقت الاتصال، يحتاج تأكيد حدود الانتهاء عملياً مع ساعة الراوتر. [assumption] (تفسير إعدادَي `starts-when` و`validity` في المصدر أعلاه)
- `uptime-limit` يحدد إجمالي الوقت الذي يبقى فيه المستخدم نشطاً؛ وسجل الجلسة يصف `uptime` بأنه إجمالي وقت الجلسة المسجل. [confirmed] ([User Manager — Limitations / Sessions](https://help.mikrotik.com/docs/spaces/ROS/pages/2555940/User+Manager))
- `transfer-limit` يحدد مجموع التحميل والرفع بالبايت؛ `download-limit` و`upload-limit` حدان منفصلان لكل اتجاه. [confirmed] ([User Manager — Limitations](https://help.mikrotik.com/docs/spaces/ROS/pages/2555940/User+Manager))
- «m» في وصف الباقة ليس قيمة بايتات مثبتة من الوصف وحده؛ نقرأ القيمة الفعلية ولا نفترض هل المقصود وحدات عشرية أو ثنائية. [assumption]
- توثق مايكروتيك ضرورة محاسبة الجلسات وتحديثاتها الدورية لتبديل الحدود أو فصل الجلسات عند بلوغ الحدود، وقبول طلبات الفصل على الراوتر لفصل جلسة نشطة. [confirmed] ([User Manager — Limitations](https://help.mikrotik.com/docs/spaces/ROS/pages/2555940/User+Manager))
- `shared-users` يحدد عدد الجلسات المتزامنة، وقد تتجاوزه إعدادات الباقة `override-shared-users`؛ تعدد الجلسات يؤثر في اختبار استهلاك الوقت والحجم. [confirmed] ([User Manager — Users / Profiles](https://help.mikrotik.com/docs/spaces/ROS/pages/2555940/User+Manager))
- لم يثبت هذا التحقق تطابق دلالات الحقول في User Manager القديم v6؛ وثيقة v7 الحالية وترحيل قاعدة البيانات ليسا دليل تطابق كامل. [confirmed] (حدود هذه المراجعة؛ ليست حكماً بعدم دعم v6)

### اختبار مطلوب قبل اعتماد التنفيذ [assumption]
- قراءة الإصدار والحزمة وقيم الباقة الفعلية دون نسخ بيانات الدخول إلى ملفات المعرفة.
- جلسة ثم فصل وإعادة اتصال: التحقق من تراكم وقت الاتصال وعدم احتساب وقت الانقطاع ضمنه.
- تحميل ورفع معلومَين: التحقق من جمع الاتجاهين وقيمة حد البايتات.
- التحقق من بدء الصلاحية عند أول دخول ومن الانتهاء بالوقت أو الحجم أو الصلاحية، دون افتراض فصل لحظي غير مقاس.
- اختبار التزامن وتحديث المحاسبة والفصل، وتكرار الاختبار لكل إصدار مطلوب؛ لم تجر تجربة على راوتر حقيقي ضمن هذه المراجعة. [confirmed]

## تنبيه لتصحيح سابق مقترح
- صياغة أن API وحدها بديل نفق لأجهزة v6 في [ملاحظات H-008](hypotheses.md) غير كافية: API تحتاج مسار وصول آمناً. [assumption] (استنتاج من فصل بروتوكول الإدارة عن الاتصال)
- DDNS يثبت اسم الوصول ولا يتجاوز CGNAT؛ يلزم تصحيح صياغة القاموس لاحقاً بعد مراجعة الوثائق الخاصة بالخدمة. [assumption]
- [confirmed] وافق المؤسس لاحقاً على خطة تحليل دورة الكرت التي تشمل تحديث [الحالة](../05-operations/status.md)؛ بقيت التصحيحات التقنية السابقة مقترحات ولم تعدل القرارات المعتمدة.
