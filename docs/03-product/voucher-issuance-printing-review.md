# دراسة إصدار الكروت وطباعتها وقوالبها

**الملخص:** [confirmed] طلب المؤسس دراسة الكروت أولًا وتأجيل صفحة Hotspot؛ لا تنفيذ أو اعتماد بنية أو سياسة جديدة.
[confirmed] القواعد السابقة مصدرها الملفات المرتبطة؛ المقترحات التالية [assumption] وليست مواصفات بناء معتمدة.

## الموجود والفجوة
- [confirmed] المصدر الحالي `src/lib/card-actions.functions.ts` يتيح إجراءات كرت موجود وإجراءات جماعية وإضافة/تعديل/حذف الباقات؛ لا يحتوي مسار إصدار دفعة جديدة.
- [confirmed] `src/components/dashboard/card-row.tsx` و`card-detail.tsx` يعرضان معلومات الباقة مع الكرت؛ الحاجة هي اكتمال العرض واتساقه لا إنشاء الربط من الصفر.
- [confirmed] `src/lib/card-style.ts` يحفظ نمط الرمز ويولّد أمثلة معاينة؛ ليس مولد إصدار آمنًا أو محرر قالب طباعي.
- [confirmed] بيانات المراقبة الحالية لا تحفظ كلمات مرور الكروت؛ لهذا لا تكفي لطباعة كلمة مرور مختلفة عن الرقم، ولا نغيّر كلمة مرور كرت قديم لاستعادتها.
- [confirmed] RouterOS يتيح إنشاء حساب Hotspot مع profile والحدود؛ [مرجع الحساب](https://manual.mikrotik.com/docs/cli-reference/ip/hotspot/user/). إنشاء دفعات User Manager موثق أيضًا، لكن توافر الأمر وشكله يجب فحصهما لكل إصدار؛ [مرجع الأمر](https://manual.mikrotik.com/docs/cli-reference/user-manager/user/add-batch-users/).

## نطاق مقترح
- [assumption] إصدار دفعات لكلا النظامين مع اختيار الراوتر والباقة والعدد ونمط الرموز، وفق القواعد السابقة لا نسخها هنا.
- [assumption] قوالب جاهزة قابلة للتعديل وخلفيات صور يرفعها صاحب الشبكة، ومعاينة كرت وورقة وطباعة PDF.
- [assumption] تنظيم الكروت بحسب الدفعة والباقة والتحديد للطباعة؛ لا إضافة بيع أو تحصيل أو إدارة نقاط بيع ضمن هذا النطاق تلقائيًا.
- [assumption] إصدار مستأنف وآمن على الأجهزة الضعيفة؛ ليس إرسال آلاف الإضافات في تشغيل واحد.

## رحلة الإصدار المقترحة
1. [assumption] اختيار الراوتر والنظام والباقة؛ عرض السعر والحجم ووقت الاتصال والصلاحية والسرعة والتزامن بشكل منفصل، مع إظهار القيم غير المقروءة بدل اختراعها.
2. [assumption] تحديد العدد ونمط الرموز ومعاينة أمثلة معلّمة بوضوح؛ مصدر النمط وقواعده في تحليل الإصدار المرتبط.
3. [assumption] مراجعة الملخص وتأكيد الإصدار؛ تحقق الراوتر من تعارض الأسماء، ولا يستبدل حسابًا موجودًا.
4. [assumption] متابعة عدد المطلوب والمؤكد والفاشل وغير المحسوم؛ نجاح الطلب لا يساوي نجاح إنشاء الحسابات.
5. [assumption] تجهيز طباعة الحسابات المؤكدة فقط؛ استمرار الإصدار من الناقص، لا إعادة إنشاء الدفعة كلها.
- [assumption] يلزم معرّف دفعة وطلب ثابت وتأكيد لكل جزء وربط كل اسم بنتيجته؛ إذا ضاع الرد نفحص وجود الحساب قبل الإعادة. سياسة حذف دفعة خاطئة تبقى حسب القواعد السابقة.
- [assumption] إلغاء العمل يوقف الأجزاء التي لم تبدأ؛ لا يدعي إزالة حسابات سبق إنشاؤها. الإيقاف والحذف عمليتان منفصلتان.

## تعديل الباقة وعرضها
- [assumption] عند تعديل باقة نوضح أثر التعديل على الحسابات المرتبطة؛ لا وعد بأن التعديل يخص الكروت الجديدة فقط، لأن الأثر يختلف بين النظامين وحدود الحساب والبروفايل.
- [assumption] فصل «الباقة الحالية على الراوتر» عن «بيانات الإصدار المطبوعة»؛ تعديل الاسم أو السعر لا يعيد كتابة ورق طُبع سابقًا.
- [assumption] الوجهة تحدد بـ الراوتر + النظام + الباقة، لا الاسم وحده؛ الكرت بلا باقة معروفة يظهر بهذه الحالة لا كباقة بلا حدود.
- [assumption] الملخص الخارجي: رقم، باقة، حالة، متبقٍ؛ التفاصيل: المخصص والمستخدم والمتبقي ومصدر القيم وحداثتها. اختيار الباقة وتصفية الدفعة لا يخفيان البحث والحالات الحالية.

## القوالب والصور
- [confirmed] رفض المؤسس القوالب المنفذة بتاريخ 2026-11-12، 03:08 UTC لأنها لم تعكس أمثلة التصميم المرسلة؛ لا يعاد تقديم نفس التكوين المبسط كحل مقبول. هذا تصحيح للعرض، لا رفض لوظائف الإصدار أو الأرشفة.
- [assumption] البداية ليست محرر تصميم حرًا: قوالب جاهزة مع الشعار واللون والحقول والمقاس، وخيار صورة خلفية مع وضع الحقول فوقها.
- [assumption] بيانات الدخول نص حقيقي فوق الصورة وليست صورة مولّدة؛ هذا يمنع رموزًا خاطئة ويحافظ على وضوح الطباعة.
- [assumption] صورة كرت مكتمل تحتوي رقمًا قديمًا لا تتحول تلقائيًا إلى قالب نظيف؛ نطلب أصلًا بلا رموز أو نخفي المنطقة بشكل واضح بعد مراجعتها.
- [assumption] الورق المطبوع مسبقًا يحتاج وضع «البيانات فقط» دون إعادة طباعة الخلفية؛ تفاصيل المعايرة في تحليل الطباعة المرتبط.
- [assumption] محرر الهاتف يوفر قائمة حقول وتحديد مواضع بالأرقام والمحاذاة بدل السحب وحده؛ الحاسوب يتيح سحبًا مع أدوات دقيقة.
- [assumption] الحقول الاختيارية: اسم الشبكة والباقة والسعر والحجم والوقت والصلاحية والرقم وكلمة المرور ورقم الدفعة؛ إدراج معلومة يعتمد على توافرها وموافقة المالك.
- [assumption] QR اختياري فقط بعد حسم فائدته؛ لا يضع كلمة المرور في رابط عام أو يَعِد بدخول تلقائي قبل اختبار صفحة الشبكة.

## الطباعة والتصدير
- [assumption] PDF بمقاسات فعلية، خطوط عربية مضمنة ورموز بأرقام لاتينية واتجاه LTR؛ لا تصدير كل الورقة كصورة منخفضة الدقة.
- [assumption] عرض المقاس والصفوف والأعمدة والهوامش والمسافات وعدد الصفحات ومناطق القص، مع حفظ إعداد الطابعة منفصلًا عن القالب.
- [assumption] طباعة ورقة اختبار أولًا ثم تأكيد المحاذاة؛ 100% / Actual size دون ملاءمة آلية تغيّر المقاس، مع بقاء فحص الطابعة الفعلية ضروريًا.
- [assumption] يمكن اختيار دفعة أو كروت محددة أو صفحات لإعادة الطباعة؛ إعادة الطباعة لا تولد حسابات أو تجدد الرصيد.
- [assumption] إنتاج PDF أو إغلاق نافذة الطباعة لا يثبت خروج الورق؛ التفريق بين «ملف مجهز» و«أكد المالك الطباعة».
- [assumption] ملف PDF جاهز هو الأساس عبر الهاتف؛ لا ضمان طباعة مباشرة لكل طابعة أو متصفح، وتحتاج الحرارية نطاقًا ومعايرة مستقلين.

## حماية الرموز: نقطة حسم قبل البناء
- [confirmed] كلمة المرور المختلفة ليست موجودة في بيانات المراقبة؛ عدم تخزينها قاعدة حالية في AGENTS.md وليست إذنًا لإنشاء أرشيف كلمات مرور.
- [assumption] الخيارات للمراجعة: كشف وطباعة مرة واحدة دون أرشيف قابل للاسترجاع، أو خزنة خاصة مشفرة ومحدودة الوصول والمدة باعتماد تغيير سياسة مستقل.
- [assumption] خيار المرة الواحدة يحتاج تصميمًا للفقد أثناء التحديث أو انقطاع المتصفح قبل الحصول على الملف؛ لا يعد حلًا موثوقًا وحده للدفعات الكبيرة قبل معالجة الاسترداد.
- [assumption] الحسابات ذات الرقم وكلمة المرور المتطابقين لا تحتاج استرجاع سر مختلف بعد تأكيد هذا النمط؛ لا يُستنتج النمط من الرقم وحده.
- [assumption] PDF والصور التي تحتوي الرموز أسرار دخول، ولو لم نخزن كلمات المرور في جدول؛ لا روابط عامة أو سجل طلبات يحتويها أو حفظ تلقائي محلي. تنزيل المالك ملفًا لا يمكّن المنصة من سحبه من جهازه.
- [assumption] قيود حجم الصور ونوعها وفك ترميزها والعزل بين الملاك ومعالجة الملفات المرفوعة تدخل مراجعة الأمان قبل التنفيذ.

## مراحل دراسة التنفيذ المقترحة
1. [assumption] حسم سياسة أسرار الطباعة وأثر تعديل الباقات وفحص قدرات v6/v7 على راوتر اختبار فقط.
2. [assumption] إصدار دفعات مؤكدة وربطها بالباقة مع حالات الاستئناف والفشل الجزئي.
3. [assumption] قوالب جاهزة وPDF وورقة اختبار.
4. [assumption] خلفية مرفوعة ومعايرة ورق مطبوع مسبقًا وإعادة طباعة وفق السياسة المعتمدة.
- [assumption] التكلفة تشمل معالجة الصور وملفات الطباعة وحماية الأسرار ودعم الطابعات؛ لا سعر أو حد أعداد أو وعد أداء مقرر في هذه الدراسة.

## معايير قبول قبل الادعاء بالجاهزية
- [assumption] حسابات v6/v7 مؤكد إنشاؤها بالباقات الصحيحة في كلا النظامين؛ انقطاع وإعادة الطلب لا يكرران الحسابات ولا يستبدلان أسماء موجودة.
- [assumption] الدفعات الكبيرة لا تعيد مشكلة المعالج؛ وتظهر نتيجة الأجزاء الفاشلة وغير المحسومة دون نجاح كاذب.
- [assumption] الملف يطابق الرموز والباقة والعدد؛ أطول رمز وأرقام تبدأ بصفر والعربية تبقى مقروءة، وإعادة الطباعة لا تعدل الراوتر.
- [assumption] اختبار ورقة فعلية ومعايرة قالب مرفوع ومنع وصول مالك لرموز مالك آخر.
