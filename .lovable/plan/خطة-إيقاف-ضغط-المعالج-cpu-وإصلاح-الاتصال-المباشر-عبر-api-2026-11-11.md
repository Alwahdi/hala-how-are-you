# خطة: إيقاف ضغط المعالج (CPU) وإصلاح الاتصال المباشر عبر API

## الخلاصة
هذا تشخيصي من بيانات راوترك الحقيقي (RB2011، RouterOS 6.49.17، فيه 3,117 كرت User Manager):

1. **المعالج 100% سببه سكربتاتنا، وأنت محق.**
   - قبل 06:46 كان المعالج 2–3%. بعد إعادة الربط صار يصل 100% في أغلب القراءات.
   - قراءة كروت User Manager تأخذ حوالي **10 دقائق** على هذا الراوتر، والسكربت يبدأ كل **5 دقائق**. الراوتر يبدأ نسخة جديدة قبل ما تخلص القديمة، فتتراكم النسخ ويبقى المعالج مشغولاً.
   - السكربت يسأل الراوتر عن كل كرت لوحده. في User Manager v6 كل سؤال يحسب الاستهلاك من سجل الجلسات القديمة، وهذا ثقيل جداً على معالج RB2011.
   - قراءة «المتصلين الآن» تفحص سجل الجلسات القديمة كله كل 5 دقائق.

2. **«لم يتم الاتصال عبر API» ليس بسبب منفذ مقفل.**
   - جربت من الإنترنت: المنفذ 8778 مفتوح ويرد خلال ثلث ثانية.
   - المشكلة أن الخادم يسجل الدخول ثم يطلب في نفس المحاولة كل كروت User Manager مع استهلاكها، ويعطي المحاولة كلها 9 ثوانٍ. الراوتر ما يلحق، فتُسجَّل «انتهى الوقت» ويظهر كأنه غير متصل.
   - الأسوأ: الراوتر يكمل الحساب بعد ما ننقطع، والخادم يعيد المحاولة كل 4–5 دقائق. هذا يزيد ضغط المعالج.

## خطوة فورية تقدر تسويها الآن (قبل الإصلاح)
الصق في Terminal الراوتر. هذا يوقف النسخ المتراكمة ويخفف القراءة إلى كل 30 دقيقة مؤقتاً، ولا يحذف أي كرت:
```text
/system script job remove [find where script="mikro-um"]
/system scheduler set [find name="mikro-um"] interval=30m
```

## ماذا سأبني (بعد موافقتك)
1. **لا تراكم أبداً:** كل سكربت يتأكد أولاً أن نسخة سابقة منه ما زالت تعمل، فيتوقف بهدوء ولا يبدأ نسخة ثانية.
2. **قراءة أخف بكثير لـ User Manager v6:**
   - طلب واحد يرجع كل الكروت بالحقول المطلوبة فقط، بدل سؤال كل كرت لوحده (أجربه على v6 الافتراضي، ومع بديل آمن إذا ما اشتغل).
   - «المتصلون الآن» يُقرأ من قائمة Hotspot active (خفيفة جداً)، بدل فحص سجل الجلسات القديمة كله.
   - مهلة قصيرة بين كل دفعة وأخرى، فلا يبقى المعالج مشغولاً بشكل متواصل.
3. **سرعة تناسب حجم الشبكة:**
   - المتصلون والباقات: كل 5 دقائق.
   - قراءة كل الكروت للشبكات الكبيرة (أكثر من 1,000 كرت): كل 30 دقيقة.
   - الكرت الذي تجدده أو توقفه أو تحذفه من التطبيق يتحدث فوراً من رد الراوتر، فلا تنتظر.
4. **اتصال API صحيح وخفيف:**
   - التحقق من الاتصال يصير: دخول + معلومات الراوتر فقط (أقل من ثانية).
   - لا نطلب كروت User Manager عبر API أبداً، لأن سكربت الراوتر يقرأها أصلاً.
   - مهلة لكل أمر بدل مهلة واحدة للكل.
   - إذا تكرر الفشل، ننتظر 30 دقيقة قبل المحاولة التالية بدل 4 دقائق.
   - الشاشة تقول السبب بوضوح. مثلاً: «المنفذ مفتوح لكن الراوتر بطيء في الرد» أو «كلمة سر مستخدم القراءة لا تطابق».
5. **مراقبة:** نسجل كم أخذت آخر قراءة للكروت، ويظهر في صحة الراوتر، مثلاً «آخر قراءة أخذت 40 ثانية». وتنبيه إذا صارت أطول من اللازم.
6. **تحقق:** على RouterOS 6.49.17 الافتراضي فيه 3,000 كرت User Manager وجلسات كثيرة، و7.16.2. أقيس مدة القراءة والمعالج قبل وبعد، وأضيف اختبارات للقواعد (منع التراكم، الوتيرة حسب الحجم، الانتظار بعد الفشل).
7. **بعد النشر:** ضغطة «إعادة الربط» مرة واحدة على الراوتر لتصل السكربتات الجديدة. أسجل القرار D-037 وأحدّث الحالة.

## ملاحظة جانبية
راوترك الثاني «الرئيسي» (v7) يرفض دخول مستخدم القراءة: كلمة السر عندنا غير اللي على الراوتر. «إعادة الربط» عليه تصلحها، والشاشة ستقول ذلك بوضوح بعد الخطوة 4.

## تفاصيل تقنية
- منع التراكم: `:if ([:len [/system script job find where script="mikro-um"]] > 1) do={:error "busy"}` في أول السكربت (نفسه لـ mikro-cards).
- v6: `/tool user-manager user print as-value` مع الحقول المطلوبة فقط، أو أسرع بديل يثبت بالقياس. المتصلون من `/ip hotspot active`، ويطابقهم الخادم بالاسم مع كروت User Manager.
- الوتيرة: السكربت يعدّ الكروت (`count-only`، رخيص). إذا كانت أكثر من 1,000، يقرأ القائمة الكاملة كل سادس تشغيل فقط (عداد global)، وإزالة الكروت المختفية تبقى على أساس القراءة الكاملة.
- `checkOne`: أوامر BASE مختصرة (resource, identity, hotspot active)، وإزالة أوامر UM. `apiSession` بمهلة لكل أمر. `shouldTryDirect` بانتظار متزايد بعد timeout.
- مدة القراءة: من بداية التشغيل إلى دفعته الأخيرة، تُحفظ في سجل التشغيل الموجود.
